> 上游 Git tree：`24621dbcc59e205a7faadb0e06d540f91712b5cc`  
> 范围：24 个 `principle-*` Skill。以下是按各 Skill 主文件整理的中文解读；引用的原则之间存在组合关系，不应孤立执行。

## A. 诊断与根因

### 1. Attack the Premise（质疑前提）

**触发：** 两次或更多基于同一前提的修复，在同一个门禁失败。

先把共同前提写成一句话，再设计一个能区分“前提成立 / 不成立”的可重复观测。若前提被否定，停止沿该前提继续修补；若被确认，再沿根因链追问。重点是避免第三次重复押注同一个已被反证的假设。

### 2. Fix Root Causes（修复根因）

**触发：** 调试问题。

从症状向前追踪，找到系统第一次做错决定的位置。先复现，再逐层问 Why；卡住时增加仪表、读取真实状态。区分“合法但未处理的状态”和“本不应该存在的错误状态”：前者应在处理边界补支持，后者应修复状态产生源头。特别关注重启后才出现的问题，其根因可能在持久化状态。

### 3. Explain the Number（解释数字）

**触发：** 测量、报告或依据性能 / Eval 数字做决策。

测量前写清楚数字会改变什么决策、噪声范围和预期结论；测量后解释“为什么不是两倍”，找出真实限制资源；排除错误、缓存、跳过工作、未运行代码、负载发生器瓶颈和端到端占比过小等假象。报告保留样本数、波动范围和限制因素。数字本身不是证据，数字背后的测量链才是。

## B. 边界、状态与类型

### 4. Boundary Discipline（边界纪律）

**触发：** 接入配置、CLI、网络协议、外部 API、框架适配或错误处理。

在系统边界做解析、校验、类型收窄和错误处理；进入内部后信任已建立的类型，不在每层重复验证。业务逻辑尽量是纯函数，框架和 Shell 只负责接线。对 BMC 很有价值：DBus / JSON / 配置文件入口做严格解析，业务模块处理已规范化的领域对象。

### 5. Model the Domain（用领域模型表达问题）

**触发：** 有状态逻辑、条件分支增多、跨文件重复状态假设。

用状态机、类型、注册表、判别联合、Reducer、事件模型、队列、索引或领域模块表达真实业务规则。目标是让非法状态无法表示、删除分散分支。不要为抽象而抽象：如果当前逻辑清晰、局部且没有扩张迹象，朴素代码更好。

### 6. Type System Discipline（类型系统纪律）

**触发：** 设计类型、函数签名或静态类型代码。

让编译器拒绝非法状态、原语混用和未处理分支。语义不同的字符串 ID 应使用不同类型；外部输入在边界解析成内部类型；权威 Schema 存在时从 Schema 派生类型，不手写平行定义。

### 7. Make Operations Idempotent（操作幂等）

**触发：** 命令、生命周期步骤、处理循环会遇到崩溃、重启和重试。

每个状态变更都要回答“执行两次会怎样”“上次在任意一步崩溃后再执行会怎样”。从当前实际状态推导目标差异，只应用缺失部分。临时文件、锁、半写记录和任务 Claim 必须能被后续运行识别和协调；例如先写临时文件，再原子 Rename 到目标位置。

### 8. Separate Before Serializing Shared State（先隔离，再串行化）

**触发：** 多个并发 Agent / 进程可能写同一文件、分支、Key 或状态对象。

先判断它们是否真的需要同一个可变对象。若只是在发布独立事实，应各写自己的文件 / Key / Worktree，最后在读取或汇总边界合并。只有共享写入确实是业务不变量时，才用锁、单写者、顺序阶段或 CAS 强制串行。Prompt 约定不是并发控制。

## C. 架构与演进

### 9. Foundational Thinking（基础先行）

**触发：** 写逻辑之前设计核心类型、数据结构、并发边界或工作顺序。

先把数据形状设计正确，再写逻辑。结构性决策保护未来选择空间，代码级决策保护简单性。CI、Lint、测试设施和共享类型等让后续阶段都受益的基础设施应先搭好。每个增量应形成完整抽象或加深既有抽象。删减复杂度优先于搭建新脚手架。

### 10. Redesign From First Principles（从第一性原理重设计）

**触发：** 把新需求集成进已有设计。

不要简单把新需求补丁式塞进旧结构。假设需求从第一天就是前提，重新推导应有的设计，再将变化传播到类型、文档、示例和理由说明。整体重新设计，按可验证的小步交付。

### 11. Outcome-Oriented Execution（面向结果执行）

**触发：** 有明确阶段边界的计划性重写和迁移。

优化最终可验证状态，而不是每个中间态都看起来平滑。允许计划内、限定范围且可回滚的中间破坏；明确哪些阶段允许暂时不兼容，保留高信号检查，最后做完整静态和运行验证。防止临时兼容层在迁移后变成永久债务。

### 12. Migrate Callers Then Delete Legacy APIs（迁移调用者后删除旧 API）

**触发：** 内部 API 改版，但旧调用者仍存在。

在同一迁移波次中更新调用者并删除旧 API，不长期保留双路径或兼容垫片。同步更新测试以断言新契约，删除只保护旧实现细节的测试。适用前提是没有外部兼容承诺，项目能够接受协调式破坏变更。

### 13. Subtract Before You Add（先减后加）

**触发：** 新增、重构或重写之前。

先删除死代码、冗余校验、无效引用和重复 Prompt，再建立新能力。优先按真实使用情况设计，不为猜测中的边缘情况增加复杂度。目标是让系统在相同或更小表面积下更简单、更有能力。

### 14. Laziness Protocol（懒惰协议）

**触发：** 评审 Diff、重构或想增加抽象 / 层次 / 信号透传时。

把决策收敛到单一事实来源，减少 Diff 和样板代码，优先删除而非增加。不要把同一个选择复制到多个地方。最小改动优于为了“优雅”增加不必要的结构。

### 15. Minimize Reader Load（降低阅读负担）

**触发：** 代码难以追踪或需要理解多个层次的状态。

从两个维度衡量可维护性：追踪层数，以及读者必须记住的隐藏 / 可变状态。折叠单调用者包装层、无意义透传层和没有第二实现的适配器；缩小状态作用域，优先纯函数、局部变量和派生状态。读者应能快速回答“X 从哪里来”“谁能改变 X”。

### 16. Experience First（体验优先）

**触发：** 产品、UX 或功能范围权衡。

当实现便利与用户体验冲突时优先用户体验。少而精，原型先行，打磨交互反馈、错误状态、对齐和核心工作流。这里的“用户”也包括调用库的同事和维护代码的下一位工程师。

### 17. Exhaust the Design Space（穷尽设计空间）

**触发：** 新颖 UI 交互或没有先例的架构决策。

先做 2–3 个竞争方案并排比较，再选定结构。避免第一次想到的方案过早锁定设计。它是 Architect / Arena 的设计探索原则。

## D. 执行、验证与协作

### 18. Build the Lever（先造杠杆工具）

**触发：** 任何非琐碎编辑、迁移、分析或检查。

先手工完成一个样本以学会操作，再构建脚本、Codemod、生成器或可复用 Skill。工具必须可重复运行，并通过与手工样本 Diff 证明正确。确定性工具优于让多个 Agent 手工做重复工作。任务结束后仍有价值的杠杆工具应提交。

### 19. Prove It Works（证明它有效）

**触发：** 完成任务、准备声明完成之前。

直接检查真实产物，不以编译成功、文件时间戳、缓存截图或 Agent 自述代替。尽可能将验证写成确定性脚本并保存输出。若验证失败，也要先检查观测方式是否正确。

### 20. Test Behavior, Not Implementation（测试行为而非实现）

**触发：** 新增、修改或保留测试。

测试要断言调用者 / 用户能观察到的行为。做两个思想实验：破坏行为时测试是否失败；只改变内部实现而保持行为时测试是否仍通过。前者不失败说明测试太弱，后者失败说明测试绑死实现。测试应通过真实接口驱动代码，预期值来自需求契约。

### 21. Sequence Verifiable Units（按可验证单元排序）

**触发：** 多步骤工作、迁移、批量修改、Commit / PR 堆栈。

把工作拆成小单元，每个单元都从已知良好状态开始，做一次变更、运行检查，通过后才进入下一单元。交付顺序也应让审查者能重放论证，例如先失败测试、后修复；先基线、后优化；先删减、后重构。

### 22. Guard the Context Window（保护上下文窗口）

**触发：** 上下文接近饱和、大文件、大输出、长会话或 Fan-out 规划。

限制每阶段文件数量和工作范围，把大体量原始产物交给子 Agent / 专用工具处理，主线程只保留摘要和决策相关证据。避免上下文膨胀导致推理质量下降或压缩遗漏。

### 23. Never Block on the Human（不要在可逆工作上等待人）

**触发：** 对可逆执行工作犹豫是否要询问用户。

对写代码、编辑文档、拆任务等可审查、可回滚的动作，先作合理决定并继续，再向用户展示结果。产品方向仍由用户决定；强制 Push、删除生产数据、发送外部消息等不可逆操作仍需明确授权。

### 24. Encode Lessons in Structure（把经验编码进结构）

**触发：** 同一条指令第二次出现，或发现重复纠正。

优先将规则固化为架构、类型、Lint、元数据、运行时检查或脚本，而不是再加一段说明文字。若规则无法结构化编码，才把指令写得更显眼并给出反例。结构性问题只做结构性修复。

## 5. 原则之间的关系

这些原则不是 24 条同级口号，而是可组合的工程约束：

- **发现问题：** Attack the Premise → Fix Root Causes。
- **建立可信观测：** Build the Lever → Explain the Number → Prove It Works。
- **塑造数据与边界：** Boundary Discipline → Model the Domain → Type System Discipline。
- **管理并发：** Foundational Thinking → Separate Before Serializing Shared State → Make Operations Idempotent。
- **控制复杂度：** Subtract Before You Add → Laziness Protocol → Minimize Reader Load。
- **安全演进：** Redesign From First Principles → Migrate Callers Then Delete Legacy APIs → Outcome-Oriented Execution。
- **可验证交付：** Test Behavior Not Implementation → Sequence Verifiable Units → Prove It Works。
- **持续改进：** Encode Lessons in Structure，将一次教训变成长期机制。

## 6. 对 BMC / Lua 研发的落地启示

| P-Stack 原则 | BMC 工程落点 |
|---|---|
| Boundary Discipline | DBus / JSON / 配置入口统一解析和校验，内部业务使用确定类型 |
| Model the Domain | 资源状态、同步状态和 IPMBETH 链路状态优先用状态机表达 |
| Type System Discipline | D-Bus 签名、资源树 Schema、Lua 数据结构统一定义，减少平行常量 |
| Idempotency | 配置同步、启动恢复、重试、导入导出支持重复执行 |
| Separate Before Serializing | 每个 Agent / Worker 使用独立 Worktree、日志和决策文件 |
| Fix Root Causes | 先复现并定位状态首次变错的位置，不用重试和吞错掩盖根因 |
| Prove It Works | 真实设备、总线读回、Redfish 查询和日志证据共同验证 |
| Test Behavior | 测外部 DBus / Redfish 行为，不绑定 Lua 私有函数调用顺序 |
| Sequence Verifiable Units | 接口、实现、配置和测试分小步提交，每步可构建验证 |
| Encode Lessons in Structure | 将反复出现的代码评审意见沉淀到公共常量、Schema、Lint 或检查脚本 |

## 7. 研究边界

本文件逐项覆盖 24 个原则主文件。部分原则本身是简短规则，详细执行语义还依赖相互引用的 Skill、Reference、Script 和测试；后续应结合这些引用做交叉审计，不能只凭原则标题推断所有细节。
