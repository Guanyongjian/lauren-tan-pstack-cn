# 措辞 prompt

prompt 陈述意图和完成的检查。playbook 提供步骤，所以几句平实的话比一份规格书更好。

## 要放入的内容

- 目标。说明哪里不对，或 user 想要什么。
- 完成检查。它能通过或失败。「让它更好」和一段时长都不是检查。
- 要展示的证据。要求真实的命令输出、flow 的视频、存储的值，或改动前后的数字。
- user 已经知道的东西。症状、复现步骤、log 或链接能省去 agent 一次搜索。
- 真实约束。「先复现」「先不要改任何 code」「行为零变化」「继续之前让我 review」，每一条都会改变 agent 的做法。

## 不要放入的内容

- 怎么做。说要达到什么，给 agent 留下寻找更好方法的空间。
- skill 或步骤列表。手写的顺序会丢掉或重排 playbook 保留的步骤。只有要覆盖某个选择时才点名 skill。
- user 对原因的理论，直到 agent 重述问题。一个已经陈述的猜测会缩窄搜索范围。

## 先加载 context

- 对混乱的报告，要求 agent 在做任何其他事情之前，用自己的话、以平实的语言重述底层问题。误读会在任何 code 出现之前显现。
- 在新的 chat 中，用 `/recall` 找回同一主题上以前的工作。旧 chat 保存着新 agent 没有的 context。
- 改动不熟悉的 code 之前，先用 `/how` 了解机制，用 `/why` 了解原因。没有追踪过 mental model 的 agent 会在第一个看似合理的位置修症状。
- 用 `/teach` 为某个选择做论证，例如「说服我它修的是原因而不是症状」。论证比摘要更容易检查。

## 先设计，再计划

- 绝不接受第一个设计。要求几个选项的 prototype，UI 要附截图或视频，然后根据证据选择。
- 让 prototype 回答开放问题。不要对抽象计划做对抗性 review，因为 reviewer 会编造永远不会发生的风险。
- 对共享 package 或 API，先要 README 或教程，再回到 code。doc 成为 agent 用来检查自己的目标。
- 只在设计定下来之后才要求计划。计划的每一步都以检查结束。

## 简短跟进

- 一旦 chat 中已有 task，「做吧」「继续」「一直做到完成」就已经是完整的 prompt。
- 主题改变时先说「新任务」。否则 mode 会把 message 当作下一步。

## 离开之前

- 说「我要去睡觉了」或「我要离开一会儿」，让 agent 停止提问。
- 把完成写成每一轮迭代都能运行的检查，并把这个 predicate 交给 `/loop`。
- 要求从指定 base 建一个新的 worktree。
- 预先回答 agent 会停下来问的事，例如「commit 之前不要问我」。
- 要求一份 decision log，供之后审计。
- 给出出口：「如果几小时后确实卡住，停下来写清楚原因」。

## 用一句话引导

- 重述目标：「我说的是目标是复现。我还没有要求修复。」
- 点名原则：「应用 prove it works。给我看真实输出，不是 build log。」
- 原则名有效，因为 agent 已经读过规则。它的回复会点名这条规则改变了哪个决定。
