# 设计依据模板

与类型草图一起交付的说明文字，一页以内。标题采用句式大小写，不写套话。把斜体提示替换成实际内容。

## 问题

*一个段落。说明我们要做什么，以及现有系统或约束中的哪些因素让结构并非显而易见。如果 [A 阶段](../SKILL.md#phase-a-ground-the-problem) 暴露了设计必须遵守的约束（需要互操作的现有类型、不能破坏的调用方、跨越我们边界的不变量），在这里点名，让读者看到你当时看到的同一组约束。*

## 用法（调用方视角）

*先写这一节，再写类型草图。展示使用者会读到的 README 或快速上手，以及他们自己的代码中两三个真实调用点：导入什么、调用什么、返回什么。[结构](#结构) 中的类型草图由此推导。两者必须一致；出现分歧时，让草图服从用法，而不是反过来。调用方体验就是规格，类型为它服务。*

## 结构

*推荐架构。先写数据结构，再写数据如何流经各个签名。点名承载关键作用的决策。说明哪些不变量编码在类型中、验证位于何处，以及系统刻意不做什么。明确评价接口深度：公开表面隐藏了什么复杂性、仍向调用方暴露什么、为什么接口没有超出所需规模。引用每项决策背后的原则（例如 `per boundary-discipline`），不要复述原则本身。*

## 综合决策

*由 [arena](../../arena/SKILL.md) 填写。记录哪个候选成为基础及原因、从其他候选分别吸收了什么，以及拒绝了什么、为何拒绝。*

## 已接受的权衡

*所选结构涉及的每项权衡各写一条，格式为「我们接受 X，以换取 Y」。点名任何可能被未来读者误认为疏漏的地方，包括看似过早优化或过早简化的做法。*

## 考虑过的替代方案

*必填。至少给出一个具体的替代结构，并用一行说明它为何落选。评价每个替代方案时要依据接口深度，而不只是实现是否简单。写明它向调用方暴露的复杂性和隐藏的复杂性。设计空间存在真正的竞争方案时，应列出两三个；约束已迫使答案唯一时，一个即可，并将结论写成「这是唯一可行的结构，因为……」。避免罗列同一结构的变体。本节覆盖所选结构考虑过并拒绝的设计替代方案，不涵盖其他竞技场候选。*

## 未决问题与风险

*绘制草图时发现、需要人类定夺的问题，以及开始实现前值得标出的风险。用问句而非断言表述，使人类的回答成为解决方案，而不只是评论。*

## 下一实现步骤
