### Shipping

**你负责什么能落地。独立验证每个 PR，只 land 从根开始连续的那段已验证运行，然后对 stack 撒手。**

1. **先确定用哪个 forge，再在落地之前独立验证每个 PR。** 默认用 GitHub CLI（`gh`）。如果 `command -v origin` 成功且 Origin 能解析该 repo，则所有 PR 操作都用 `origin pr`。否则留在 `gh` 上并记下这次 fallback。绝不要要求 Graphite（`gt`）。每个 PR 一个 verifier，各自是一个 Cursor cloud agent，用对应的 control skill（例如来自 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）像 user 那样跑这次改动，parent 对 head，并在该 PR 上贴出 `PASS`、`PASS+NOTES` 或 `FAIL`。只有来自未曾写过这段 code 的 agent 的 verdict 才算，因为作者检查的是他本来想建的东西。绿的 CI 和一次赞成的 bot review 都不是 verdict，因为两者都没有像 user 那样去跑这次改动。
2. **只 land 从最底下开始连续的那段已验证运行。** 从最下面那个未 merge 的 PR 往上走，在第一个没有 `PASS` 或 `PASS+NOTES` 的 PR 处停下。它下面的那些 PR 就是这一段运行，最上面那个是天花板。位于未验证 PR 之上的已验证 PR 要等，因为它不能没有下面的 code 就落地。某个 PR 若其 branch 既不包含也不依赖那段 code，就可以自己挪到 trunk 上独立落地。但它需要先拿到一个新的 verdict，因为旧的 verdict 是在那段 code 垫在下面时跑的，而 trunk 上没有那段 code。
3. **重新核对这些 verdict 是否仍然描述当前 code。** 一个 verdict 覆盖的是一个 patch，而一次链式 rebase 会把其上方每个 PR 挪到新 SHA 上，却不会让任何检查失败。在信任旧 verdict 之前，把 verdict SHA 处的 `git patch-id` 与当前 head 对比。当两个 patch 只在 test、doc 或 lint config 上有差别时，只要该 lane 所跑的东西在两个 SHA 上构建结果相同（噪声除外），其结论就仍然成立。噪声是指那种在 verdict SHA 的两次构建之间也会出现的差别，或内嵌的 commit SHA。把每种噪声连同其 file 一并报告，好让读者能复核这个判断。改动本身仍需重新检查与 review，因为旧 verdict 从没见过它。没有构建 output 的 lane（例如 dev server）无法展示这一点，所以要重跑它，并重新验证其他任何漂移之物。
4. **自底向上，一次一个 PR。** 永远先 merge 这段运行里最下面那个未 merge 的 PR，用 `origin pr merge <pr>` 或 `gh pr merge <pr> --squash`。在 Origin 上这条朴素命令还会 merge 比你点名那个之下的每个 PR；而在 GitHub 上，一个 base 仍是其 parent branch 的 PR 会 merge 进那个 branch，而不是 trunk。要回读 PR 确认结果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因为 merge 命令可能在 merge queue 只是把 PR 排了队时就报告成功，而被请求的 auto-merge 并不是一次 merge。已落地的 PR 读出来是 merged、base 为 trunk，而不是其 parent 的 branch。只对 verdict 覆盖其当前 head 的 PR 才 arm `--auto`（Origin 的 merge-when-ready 或 GitHub 的 auto-merge），因为它会落地任何就绪的 head。一次 merge 落地后，把那个 base 曾是被 merge branch 的 PR 重新指向 trunk（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），把它的 patch 挪到 merge 结果上，并用 `--force-with-lease` push。verdict 覆盖的是 patch，不是它的那些 commit，所以由 step 3 的 patch-id 规则来判定该 verdict 是否存活。等它的检查通过、verdict 存活之后再 merge 它。
5. **它在落地期间不要动这个 stack。** step 4 中对下一个 PR 的移动，是对 branch 或 base 的唯一改动，因为一次 merge 会落地其 branch 和 base 在那一刻所持有的内容，无论 verdict 如何。在 GitHub 上，用 `playbooks/babysit.md` 里的 queued watcher（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）在 `/loop` 下盯着这段运行，直到它在天花板处报 `COMPLETE`。在 Origin 上，每次 `origin pr checks <pr> --watch` 返回时，都用 `origin pr view <pr> --checks` 重读当前 PR，直到天花板读出 merged。base 在其 parent merge 时挪到 trunk 是预期行为，不是需要修复的损伤。如果某个 merge 卡住了，先查明原因再动任何东西。
6. **在天花板处停下。** 延长这段运行需要新的 verdict，所以那是重新走一遍 step 1。

**Reply：** 已验证的那段运行及其天花板、每个 PR 的 verdict 及由谁产出、什么落地了以及你如何确认、还有下一个缺口需要什么。
