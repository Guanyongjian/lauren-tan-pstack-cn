# Test Behavior, Not Implementation（测行为不测实现）

测试是关于「这段代码对其使用者做了什么」的一个主张；使用者可以是调用方、终端用户，或另一个服务。Behavior 是这些使用者通过他们所使用的接口能够观察到的东西：返回值、错误、他们能读回的状态，以及对外部系统的影响（发出一次请求、写入一行记录、发出一条消息）。Implementation 是他们观察不到的东西：私有 helper、内部调用顺序、中间数据，以及是哪个内部协作者干的活。

用两个假想的改动来检验每个测试：

- **破坏行为。** 让代码返回错误的值、跳过某个效果，或把效果做两遍。如果测试仍然通过，它什么也没证明。常见原因是：断言比 contract 更松、期望值由被测代码自己算出、重复一遍常量或 prompt 字符串却从不运行读取它的代码、以及对测试自己造出来的数据做断言。
- **改变内部实现。** 保持所有可观察结果不变，重构底层代码。如果测试这时失败，说明它被钉在实现上了。它会在每次重构时都需要重写，却仍然抓不到任何 bug。

保留那种「能抓住第一个改动、又能挺过第二个改动」的测试。其余的改写或删掉。要写出同时满足两者的测试：用具体输入，通过使用者的接口驱动代码；期望值从需求推导，而不是从跑一遍代码得出；断言 contract 所承诺的内容，不多也不少。

决定权在 contract，而不在断言的形式。当「空购物车永不扣款」是那条承诺时，断言支付客户端没有被调用，就是在测行为。要配一个确实发生扣款的用例，这样测试才能证明它看得见调用。被 mock 的外部服务收到的 payload 属于行为，因为那个服务能观察到它。对内部 helper 的调用属于实现，因为没有使用者能看见它。当没有任何记录匹配时，返回空列表就是精确答案；而当测试只是需要某个结果时，空列表就是个空心的检查。精确的 error message 会钉住没有任何调用方会去读的措辞；而调用方据以分支的 error type 才是 contract。

测试也可以钉住一个 invariant 而不是一次调用，比如某个 key 必须同时存在于两张表，或一个编译期类型检查。这个 invariant 就是行为。
